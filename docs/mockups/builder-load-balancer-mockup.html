Load balancer

A Load balancer gives a pool of identical components one address. Clients send to the address; the load balancer passes each connection to one member. It takes the plane and ports of what it serves: syslog receivers and HEC on the event-data plane, Deployment Servers on the fleet-management plane. Pick a scene, select a card to see its inspector, and change the load balancer's settings to see the review rules update.

What it can serve

Its first link decides what it serves. Every link through it must be one the client could make straight to the member, and a pool holds one kind of component.

ServesPlaneClients (send to its address)Pool membersListeners
Syslog receiversEvent dataSyslog SourceSyslog Server, Heavy Forwarder, Indexer, Edge ProcessorUDP 514, TCP 514, TLS 6514
HTTP Event CollectorEvent dataHEC Client, AWS Lambda, Azure Function, API CollectorHEC Endpoint, Heavy Forwarder, Indexer, Edge ProcessorHTTPS 8088, HTTPS 443
Deployment ServersFleet managementUniversal Forwarder, Heavy Forwarder (they phone home to its address)Deployment Server, up to 3 in a clusterHTTPS 8089
  • Refused: forwarders. A Universal or Heavy Forwarder sending S2S (9997) can't link to a load balancer. Forwarders balance across indexers themselves (autoLB), or use indexer discovery.
  • Refused: Splunk-managed members. Splunk Cloud already balances its own inputs. Link straight to the managed component.
  • Refused: mixed pools, a load balancer in front of another, and data links to one that serves Deployment Servers (or management links to one that serves data).
  • Volume passes through unchanged and splits evenly across the members. Nothing is copied.
  • Deployment Servers: clients phone home to the load balancer's address. Server classes and apps on any member apply to every client behind it.
  • Methods: a load balancer (proxy), DNS round robin, or a floating virtual IP (keepalived, MetalLB). The last two don't translate addresses and have no single box in the path.

What the views show

The load balancer is infrastructure. Views about systems and services see through it; views about networks and threats show it.

ViewWith a load balancer
CanvasOne link from each client to the load balancer, and one from it to each member. In tier grouping it sits in its pool's tier.
Network and firewall overlayClients → its address on the listener ports, and load balancer → members on the same ports.
Threat modelA component in its network zone. A zone crossing is on the client → load balancer link. New threats: denial of service when it's a single instance, information disclosure when TLS ends on it.
OV-1, OV-2, OV-3Part of its pool's operational node: no new node or needline. Its links to members show as internal flows.
CV-1, CV-2, SvcV-1 to SvcV-6, DIV-1The same results as clients linked straight to the members. Interfaces name the load balancer, and it isn't listed as a system.
Failure LabIt can be the fault target. Its stages are the fault points: virtual IP listener, health checks, member selection, client address handling and session persistence.
Inventory and packA row for it. Clients behind a deployment load balancer show it, and its Deployment Servers, as their management authority.
